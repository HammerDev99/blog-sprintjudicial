Claude Code y agentes especializados en el flujo de trabajo técnico

Cómo cambia construir software cuando la IA conoce el dominio y tiene herramientas propias

Posted by Daniel Arbelaez on Friday, January 15, 2027

El post que estás leyendo lo escribió un agente llamado blog-writer. La imagen del encabezado la descargó otro proceso automático. El frontmatter fue generado siguiendo un SPEC definido en un archivo de planning. El commit que publicó el archivo tiene un mensaje en formato convencional que ningún humano escribió. No porque el humano no pudiera — sino porque el sistema está configurado para hacerlo de esa forma, y el humano puede concentrarse en qué decir en lugar de en cómo decirlo.

Eso es lo que cambia cuando Claude Code tiene contexto del dominio y agentes especializados.

Cómo funciona el sistema en este repositorio

HammeredSolutions tiene una arquitectura de agentes construida dentro de .claude/agents/ y .claude/skills/. No es una instalación de Claude Code por defecto; es una configuración que se desarrolló iterativamente para el problema específico de mantener un blog técnico sobre legaltech con voz consistente y calidad verificable.

El agente blog-writer sabe redactar en la voz de Daniel, siguiendo las reglas del humanizer. Las reglas están codificadas. Cero paralelismos negativos del tipo “no es X — es Y”, máximo dos guiones largos en todo el post, cero dos puntos en prosa fluida, párrafos de mínimo tres oraciones. El agente no las adivina; las lee de un archivo de instrucciones que forma parte del repositorio.

El skill article-writing complementa al agente con un flujo de trabajo documentado. La secuencia es article-writing para el borrador, blog-humanizer para limpiar patrones de IA, content-reviewer para verificar tono y alineación estratégica, y deploy cuando todo pasa. Eso no es un proceso informal; es el pipeline definido en CLAUDE.md y verificable en cualquier momento.

Lo que cambia cuando el agente tiene contexto de dominio

La diferencia más grande no es la velocidad; es la especificidad. Un agente genérico sin instrucciones del dominio va a producir texto que suena a IA porque no conoce las restricciones reales. Un agente que sabe que el blog tiene cuatro categorías válidas, que los posts de la categoría Aprendiendo deben tener una analogía sostenida de inicio a fin, que el autor trabaja con TutelaBot Air a F1 78% sobre 358 tutelas y que AgilEx tiene firma Authenticode SHA256 va a producir texto que puede pasar como escrito por alguien que sabe de qué habla.

Esa especificidad tiene un costo de setup. El CLAUDE.md de este repositorio tiene cuarenta líneas de instrucciones críticas. El archivo agent_docs/project_reference.md tiene los datos concretos de cada proyecto para que ningún agente invente números. Los SPECs en PLANNING_04 tienen ángulo, estructura, fuentes y criterios de aceptación para cada post. Construir ese contexto tomó tiempo. Mantenerlo requiere disciplina para actualizar los archivos cuando cambia algo en los proyectos.

Las rarezas que el flujo no resuelve

Claude Code no es infalible y el sistema tiene puntos de fricción conocidos. El modelo puede generar colons en prosa aunque las instrucciones digan que no debe. Eso requiere verificación con Grep después de cada post generado, que es un paso manual que no se puede automatizar sin un linter de texto que entienda el contexto de la regla. Los em-dashes también aparecen a veces de más, especialmente cuando el borrador tiene listas que se reformulan como frases.

Las imágenes de encabezado requieren intervención humana o una búsqueda guiada. El sistema descarga desde URLs de Unsplash, pero elegir la imagen correcta para un post sobre scheduling en sistemas operativos versus uno sobre open source no es algo que el agente resuelva bien sin instrucción específica. A veces la primera imagen descargada funciona; a veces es genérica y hay que buscar otra.

El contexto del repositorio se carga en cada sesión pero no persiste entre conversaciones sin los archivos de memoria explícita en .claude/projects/. Eso significa que un agente que en la sesión anterior aprendió algo sobre el dominio puede empezar la siguiente sin ese aprendizaje si el archivo de memoria no fue actualizado.

Lo que vale la pena

El flujo funciona bien para tareas repetibles con criterios verificables. Escribir un post siguiendo un SPEC es una tarea repetible. Verificar que no hay colons en prosa es verificable. Actualizar el SPRINT después de cada entrega tiene un formato definido. Esas tareas antes tomaban tiempo cognitivo que ahora no toman.

Lo que sigue siendo trabajo del humano es la decisión sobre qué decir. El ángulo de cada post, la escena de apertura, la posición argumentativa del cierre, la honestidad sobre los límites de los proyectos propios. Eso no se puede delegar a un agente sin instrucciones tan específicas que terminarían siendo el post mismo. El agente ejecuta; el humano decide qué ejecutar.

Para un proyecto unipersonal como este, esa división funciona. El costo de configurar el sistema se amortiza rápido cuando el número de posts que hay que escribir es suficientemente alto.
